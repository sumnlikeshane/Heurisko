# HEURISKO — Tooling and Reuse

Research date: 31 October 2026. Status: **PROPOSED — NOT YET APPROVED**. This is research and an integration recommendation; no dependencies were installed, packages executed, repository initialized, or security benchmarks run.

## 1. Finding that changes the product strategy

Heurisko is entering an established field. **OSS Rebuild already reconstructs published packages and publishes attestations; vlt's reproduce already tests npm source reproducibility; Drydock already provides browser-based artifact diffs and line-linked supply-chain findings.** Building any of those features alone would offer limited differentiation. The credible opportunity is a unified source-to-artifact investigation that accounts for every inspected difference, separates verified relationships from plausible explanations, and preserves unresolved evidence across terminal, browser and CI. That opportunity is an engineering hypothesis to test, rather than a verified market gap. [OSS Rebuild](https://github.com/google/oss-rebuild), [reproduce](https://github.com/vltpkg/reproduce), [Drydock](https://github.com/JoviDeCroock/drydock).

Do not claim to be the first package-integrity tool, the first rebuild service, or the first package-diff UI. Differentiate through measured performance on the organizer's legitimate-build and tampered-copy cases.

## 3. Ranked build / integrate / defer decisions

| Rank | Capability | Recommendation | Reason / complexity / remaining question |
|---|---|---|---|
| 1 | Evidence/report schema and relationship accounting | **Build** | Central distinctive responsibility: one fact model used by all UIs, explicit source claims, inspection coverage, rules and evidence IDs. High design complexity; benchmark whether users understand the outputs. |
| 2 | Registry adapters and exact artifact acquisition | **Build thin adapters; integrate standard HTTP/hash libraries** | Ecosystem-specific API/identity logic belongs in Heurisko. Reimplementing tar, ZIP or cryptography adds unnecessary attack surface. Medium complexity; test redirects, scoped npm names and PyPI file variants. |
| 3 | Signature and attestation verification | **Integrate Sigstore / PyPI public APIs** | Mature specialist verification must replace custom crypto. Medium integration complexity; model trust-policy failures separately from missing provenance. |
| 4 | Archive inventory and containment | **Integrate parsers; build restrictive policy around them** | Parsing is reusable, while limits, duplicate-path policy, link handling and audit evidence are application responsibilities. High security-review priority. |
| 5 | Existing rebuild evidence | **Integrate OSS Rebuild optionally** | Avoid duplicating its ecosystem-wide infrastructure. Medium adapter work, high trust-policy responsibility. Missing coverage remains an ordinary state. |
| 6 | Local independent rebuilds | **Build constrained orchestration; evaluate OSS Rebuild / reproduce reuse** | Necessary for stronger relationships when feasible, but environment reconstruction is difficult. High complexity and separate execution isolation. |
| 7 | Deep archive/binary diagnostics | **Integrate diffoscope optionally** | Mature recursive diagnostics. Medium adapter and deployment complexity; do not let external subprocess failure erase a primary finding. |
| 8 | JavaScript structural analysis and source-map navigation | **Integrate parsers; build evidence-aware matching** | Libraries parse syntax/locations; they do not prove semantic equivalence. High analysis complexity, especially bundlers and minified code. |
| 9 | Malware/advisory/hygiene context | **Optional adapters** | GuardDog, OSV and Scorecard improve context without replacing P04. Medium integration each; noisy context must not dominate a correspondence conclusion. |
| 10 | Monitoring / notifications | **Build lightweight durable scheduling first; evaluate feed reuse** | Monitoring is an official P04 capability. Content digest/version deduplication and per-release reports matter more than a full global package index. |
| 11 | Dependency update bots | **Integrate at PR/CI boundary** | Let Dependabot/Renovate select upgrades. Heurisko reviews their exact version pairs. Low–medium boundary work; no duplicated updater. |
| 12 | Hosted scanners as core dependency | **Avoid** | Mandatory cloud accounts, unclear service availability and unrelated verdicts weaken a local evidence engine. Optional connectors remain possible. |
| 13 | Custom crypto, universal deobfuscator, arbitrary automatic builds | **Avoid as initial foundations** | Unsupported security promises and large attack surface. Specialized research can continue with explicit acceptance tests. |

“Defer” preserves a potential capability. It does not narrow the future product solely for event timing.

## 4. Concrete TypeScript foundations

These are **candidate dependencies**, not a tested lockfile. Prefer a Node/TypeScript core because the proposed CLI and React browser interface can share validated report contracts. Alternative Go/Rust cores improve binary distribution and can be reconsidered if parser/process performance or sandboxing requirements warrant them. No library choice removes the need for operating-system isolation.

|---|---|---|

Heurisko counts actual expanded bytes and entries, handles PAX names, rejects unsupported special entries and duplicate/conflicting paths. gzip decoding is separate. Latest release date not established. |

| Registry SRI | ssri, ISC. The selected team stack can use React/TypeScript for the browser and an optional Ink-based TUI, but UI library admission belongs in the product/architecture workstream. Do not make TUI dependencies necessary to run noninteractive CI.

## 5. Integration contracts

All adapters should return tool-native facts inside a common envelope: provider, tool version, input artifact digest, selected source commit/subdirectory, policy version, execution timestamp, completion status, evidence objects and errors. Preserve native classifications under provider namespaces; convert them into Heurisko findings only through documented rules.

For example, an OSS Rebuild response is not trusted merely because it exists. Validate its signature under an explicitly approved trust root, match the subject digest to the precise artifact being inspected, record rebuild identity/parameters and comparison semantics, and retain the attestation bytes. If verification is unavailable, report an unverified provider claim. A tool failure is a coverage limitation, not a clean result.

A Python adapter should accept file paths only to controlled acquired artifacts plus explicit expected publisher policy; return versioned JSON, with diagnostics on stderr. Do not pass credentials to an analysis worker or invoke shell strings derived from package metadata. Any tool that installs or rebuilds source belongs in the execution worker, never the ordinary acquisition/parser process.

Version-to-version changes, artifact-to-source differences and known-vulnerability enrichment must remain separate report dimensions. A release may be reproducible and vulnerable; non-reproducible and benign; validly attested and malicious; or unverified because evidence is unavailable.

## 6. Novelty and competitive acceptance tests

1. Compare against raw npm diff / inventory diff: does Heurisko explain legitimate transformations with specific source/build evidence while retaining unresolved regions?
2. Compare against OSS Rebuild and reproduce: does Heurisko provide useful, honest evidence when reconstruction fails or a package has no rebuild coverage?
3. Compare against Drydock: does source identity and the source-to-artifact relationship add meaningful actionable information beyond prior-version diffs?
4. Compare against GuardDog and Socket-style signals: can Heurisko distinguish a capability already present in accepted source from one introduced only in the distributed artifact?
5. Ask security engineers to reproduce a report from its evidence bundle. If they cannot, UI polish does not establish technical value.

These are proposed evaluations; no comparative results have been produced.

## 7. Admission checks and remaining gaps

Before implementing any candidate, record the exact release and digest, SPDX license/NOTICE and transitive obligations, supported runtime/platform, current advisories, release provenance where available, API stability, resource behavior and representative fixture results. Do not run broad “latest” installations or copy commands containing lifecycle execution into the default static analyzer.

Open questions: exact Node/Python compatibility; which PyPI file variants are initially supported; OSS Rebuild attestation trust and authentication policy; reproducible-build environment coverage; supported native client architectures; diffoscope packaging; guarddog v3 adapter stability; source-map package's current manifest/license; and dependency redistribution obligations. A visible GitHub license badge is useful evidence, not a completed legal or security audit.

A supplemental discovery surfaced GrepCode and other package-viewing sites, but direct retrieval was blocked or insufficient to validate capabilities. They are not qualified dependencies or confidently excluded competitors. PyRadar and reproducible-packaging research were passed to the source-matching workstream; this document does not claim their experiments were replicated.

Firecrawl was used for initial searches and official-page retrieval. Its connected account then reported insufficient credits; remaining sources were investigated through the available web retrieval service. Failed requests were not counted as evidence, and no attempt was made to bypass the account restriction.
