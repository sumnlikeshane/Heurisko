# Heurisko web application — full product scope

**Reconciled:** 1 November 2026, Asia/Kolkata. **Status:** current local web implementation, requirements and acceptance gaps. Shane and Codex own the authorized end-to-end overhaul in `apps/web`; the earlier documentation reconciliation and W0–W4 receipts remain historical checkpoints. Read the [continuation handoff](WEB_CONTINUATION.md) for the next run and the [CLI reference](CLI%20Reference.md) for today's commands.

The intended web application provides complete CLI documentation and an end-to-end browser investigation workflow with parity for supported CLI capabilities. A user should be able to understand the product, select a supported exact target, request an investigation through the shared engine, follow its progress, investigate its results and evidence, and retain/reopen/export the result. The saved-report viewer was the **first slice**. The current overhaul builds on the implemented W2–W4 flows with one task shell, guided input/review/run, a factual report overview, bounded file/finding/evidence reading, contextual save/open and user-focused documentation. The [single gap backlog](Web%20Application%20Gap%20Plan.md) owns U01–U18 dispositions and source-bound acceptance; this scope document is not another roadmap. Missing shared integrations, untested acceptance and human design approval remain open.

## 3. Complete intended journey

These are required user journeys under the existing trust rules. Current source implements the local workflow; the current backlog records acceptance and remaining gaps. Fresh browser analysis calls the existing engine through the scoped local boundary. No hosted analyzer or new transport technology is selected.

1. **Learn and prepare.** Read the source/artifact question, supported capabilities and limits; install/run locally; follow a complete CLI quickstart/reference; distinguish a fresh analysis from historical replay. Browser investigation and terminal use remain account-free in the local profile.
2. **Choose an input.** Enter a registry-qualified exact npm target, including scopes, or explicitly select a local tar/tar.gz. A package search/version chooser is a proposed convenience leading to exact selection, not a mandatory global index. Today's engine rejects ranges, aliases and dist-tags; never silently turn `latest` into an authoritative release.
3. **Set the comparison context.** Supply optional GitHub repository + full commit and package subtree, or retain the resolver's candidates/conflicts. For local replay, support the equivalent source snapshot choice and explicit labels. Show that a user override is a comparison target, not source proof. Keep downloaded metadata, expected integrity and observed digest separate.
4. **Review and start.** Show the actual supported target, options, AI availability, requested policy and storage/export effects. AI enabled cannot promise inference while the module is missing. A policy reference cannot promise an evaluator. Submit structured input to the same engine; do not execute shell command text or package-provided recipes.
5. **Follow execution.** Show real stage progress and partial/failure states. Permit the equivalent of a foreground interrupt when supported, while distinguishing cancel requested, settled report, settled error and cleanup acknowledgment that remains `not_observable`. A disconnected tab is not proof of cancellation, background operation or resume. Read-only reconnection is available within the same process; durable resume, detach and automatic retries are unsupported.
6. **Investigate the result.** Open the same validated report, show its six outcomes and separate AI state, exact identities, observation time, coverage and most useful next action. Follow files/changes → recorded spans/full members → source/provenance/build evidence. Follow findings and AI hypotheses to their actual cited bytes and back without losing investigation context.
7. **Retain, reopen and reproduce.** Preserve immutable original report bytes, bundle and referenced evidence with declared omissions. Open a prior report or portable directory without reanalysis. Offer equivalent CLI instructions with safe argument handling. A new source/configuration/retry creates a new evaluation; a historical observation is never silently refreshed.
8. **Monitor supported releases.** When the actual shared monitor exists, provide parity for supported add/run-once/status/remove operations and scheduler/failure/history visibility. Until then show unavailable state. Closing a browser or local process cannot imply continuous monitoring.

## 5. CLI and browser parity requirements

Parity means equivalent supported input/options/actions, identical engine facts and evidence, and understandable failure/output behavior. It does not mean copying terminal flags into UI labels or inventing support for unimplemented CLI commands. Browser HTTP/transport success is not analysis completion. The browser must explain the engine result corresponding to CLI 0/1/2/3 without deriving a separate verdict.

| Capability | Current CLI / local tooling | Current browser | Required parity / acceptance |
|---|---|---|---|

Separate live runs may have different observations; compare deterministic facts with equivalent inputs/configuration, not wall-clock bytes. |
